# P1-PG-03 — Transactions and isolation: reproduce anomalies

## Objective
Reproduce concurrency anomalies in PostgreSQL, then remove each with the correct tool.

## Problem
The engine updates workflow state from several places. Without understanding what a transaction does and does not guarantee, state gets lost or corrupted silently.

## Prerequisites
`P1-PG-01` (running PostgreSQL, queries from Go), `P0-GO-03` (goroutines, to run two sessions at once).
Uses: PostgreSQL and Go database access (P1-PG-01); goroutines (P0-GO-03).

## Techniques
`BEGIN/COMMIT/ROLLBACK`, isolation levels, `SELECT ... FOR UPDATE`, atomic `UPDATE ... SET x = x + 1`, constraints, retrying on serialization failure (SQLSTATE `40001`).

## What you need first
A transaction groups statements so they commit together or not at all. Isolation level decides what concurrent transactions can see of each other. In PostgreSQL the default is READ COMMITTED; REPEATABLE READ is snapshot isolation; SERIALIZABLE can abort a transaction and expects the caller to retry. Verify these statements against the PostgreSQL documentation chapter on concurrency control during the unlock; they are not to be taken on trust.

## Practical challenge
With two sessions (two `psql` windows, then two Go goroutines), reproduce: (1) a lost update on a counter, (2) a non-repeatable read, (3) write skew (two transactions each check an invariant, then both write). For each, show it under one isolation level and fix it with a different mechanism. Record the observed output.

## Deliverable
SQL scripts and a Go test per anomaly (PRJ-ENGINE or PRJ-LABS, kept in the evidence bundle), and `EVIDENCE/P1-PG-03/RESULTS.md` (from `TEMPLATES/EXPERIMENT.md`) with observed outputs and a table: anomaly × isolation level × observed? × fix.

## Acceptance criteria
1. Each of the three anomalies is reproduced deterministically (script or test), with output captured.
2. Each has a fix proven by a test that fails before the fix and passes after.
3. SERIALIZABLE test includes a retry loop that handles `40001`.
4. The results write-up (`EVIDENCE/P1-PG-03/RESULTS.md`) states which claims were observed on the learner's PostgreSQL version and which come from documentation.

## Verification
Evaluator re-runs the scripts on a fresh, empty database. Oral: "When is `FOR UPDATE` enough, and when do you need SERIALIZABLE?"; "What happens to your code if SERIALIZABLE aborts?"
