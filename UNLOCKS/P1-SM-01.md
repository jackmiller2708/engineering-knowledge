# P1-SM-01 — Instance and step lifecycle as a pure state machine

## Objective
Define the workflow instance lifecycle as a pure function, with proven invariants.

## Problem
Retries, cancellation, recovery and multiple workers all change state. If transitions are scattered through I/O code, correctness cannot be argued. A pure core can be tested exhaustively and reasoned about.

## Prerequisites
`P0-TYPE-01` (data modeled so illegal states cannot be built), `P1-DEF-01` (the step graph this machine runs over).
Uses: the workflow graph definition and validator (P1-DEF-01); the data-modeling approach (P0-TYPE-01).

## Techniques
States and events, transition tables, pure functions (no clock, randomness, I/O), returned effects as data, property-based tests, invariants.

## What you need first
A state machine has states, events and rules for which event moves which state to which state. *Pure* means the same input always gives the same output and nothing outside is touched. An *invariant* is a statement that is true in every reachable state.

## Practical challenge
Write `Apply(state, event) (newState, effects, error)` for the instance (for example Pending, Running, Waiting, Succeeded, Failed, Cancelled) and for each step (for example Pending, Ready, Running, Succeeded, Failed, Skipped). A step becomes Ready only when every step it depends on has Succeeded, as the definition says. Decide the events (start, step finished, step failed, retry scheduled, cancel requested, ...). Terminal states must be final. Time enters only as an event value.

## Deliverable
A `statemachine` package in PRJ-ENGINE with a transition table document, tests, and an invariants list (`project/design/invariants.md`).

## Acceptance criteria
1. Every (state, event) pair has a defined outcome: a new state or a typed error (exhaustive test over the full table).
2. Property test: random event sequences never reach an undefined state; terminal states never leave.
3. The package imports no `time`, `database/sql`, `net`, or random packages (checked by a test or script).
4. `project/design/invariants.md` lists at least 5 invariants, each linked to a test.
5. Cancel arriving at every state is specified and tested.

## Verification
Tests and import check. Design defense (L5): evaluator proposes "let us just add a status column and update it where needed"; learner explains the trade-offs; evaluator proposes a new event and the learner adds it, stating which invariants it affects.
